# api – Fastify service and background worker

TypeScript (Node 22, ESM). One package, two entry points:

| Entry           | Runs as            | Responsibility                                                     |
| --------------- | ------------------ | ------------------------------------------------------------------ |
| `src/server.ts` | `api` container    | HTTP API: Smithy server SDK behind Fastify, auth, chat (RAG), CRUD |
| `src/worker.ts` | `worker` container | pg-boss consumer: parse → chunk → embed guideline uploads          |

Both share the same image (`Dockerfile` target `api`) and configuration.

## How a request flows

```
nginx ─► Fastify (request id, logging, body limit)
          └─► auth middleware (JWT) ─► generated Smithy handler
                                        ├── routes by @http traits
                                        ├── validates input from constraint traits (ValidationException)
                                        ├── calls src/handlers/<Operation>.ts
                                        └── serializes output / modelled errors (restJson1)
```

- `src/app.ts` builds the Fastify instance and adapts Fastify requests to the SSDK's `HttpRequest`.
- `src/handlers/` has one file per Smithy operation. Handlers throw the typed errors from
  `@app/api-server-sdk` (`NotFoundError`, `ConflictError`, …). Anything else becomes a generic
  `InternalFailure` (the SDK never leaks internals).
- Every response carries `x-request-id`; error bodies include `requestId`.

## Configuration

See `.env.example` at the repo root; `src/config.ts` is the single place that reads
`process.env` and fails fast with a list of every problem. Notable settings:

| Variable                                                           | Meaning                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`                                                     | Postgres connection (pgvector extension is created by migrations)                                                                                                                                                                              |
| `JWT_SECRET`, `ACCESS_TOKEN_TTL_MINUTES`, `REFRESH_TOKEN_TTL_DAYS` | access-token signing and lifetimes; refresh tokens are opaque, hashed, rotated on use                                                                                                                                                          |
| `SEED_USERS`                                                       | `user:password,...` created on first start                                                                                                                                                                                                     |
| `GEMINI_*`                                                         | API key, chat model + thinking level, embedding model + dimensions (dimensions must equal the `vector(768)` column; api and worker refuse to start otherwise; a model change needs `pnpm db:reembed`), `GEMINI_TIMEOUT_MS` per-request timeout |
| `RAG_*`, `CHAT_HISTORY_WINDOW`                                     | retrieval sizes / thresholds, conversation window                                                                                                                                                                                              |
| `MAX_UPLOAD_MB`                                                    | upload limit (also the Fastify body limit)                                                                                                                                                                                                     |

## Authentication

- `POST /api/auth/login` → `{ tokens: { accessToken, accessExpiresAt, refreshToken, refreshExpiresAt }, user }`.
- Access token: HS256 JWT, `ACCESS_TOKEN_TTL_MINUTES` (15), sent as `Authorization: Bearer`.
- Refresh token: 32 random bytes, stored as a SHA-256 hash in `refresh_tokens` with a family id.
  `POST /api/auth/refresh` rotates it (old one revoked, new one issued in the same family).
  Presenting an already-rotated token revokes the entire family (theft detection).
  `POST /api/auth/logout` revokes the family. `REFRESH_TOKEN_TTL_DAYS` (7).
- Public routes are derived from the OpenAPI document (`@auth([])`): health, login, refresh, logout.
- Conversations are private to the agent who started them: list, get, send and feedback are all
  scoped to `created_by` in the service layer, and another agent's conversation answers 404.
  Companies, guidelines and corrections are shared.

## How a chat turn works (`conversations/service.ts`)

1. Persist the agent's input (customer message or instruction). Re-sending the same text right
   after a failed assistant turn reuses the stored message instead of duplicating it.
2. Build the retrieval query (short follow-ups are combined with the previous customer message)
   and fetch the top-k guideline sections of the **active** version plus similar active
   corrections, both by cosine similarity with score thresholds (`RAG_*`). When a correction
   matches, the sections its original question retrieves are appended (up to two, tagged
   `via: correction`) so a paraphrase that misses the right section can still be grounded.
   Finally the keyword rescue (Postgres full-text on a generated `tsvector` column) appends at
   most one section that the vector ranking missed but a distinctive, repeated word of the
   message points at (`via: keyword`); the vector order is never changed.
3. Build the prompt: system rules (template `prompts/chat-system.md`), the rolling summary of
   messages older than the window (if any; messages that just left the window are summarised
   first, incrementally, and the result is stored on the conversation), the last
   `CHAT_HISTORY_WINDOW` messages, and the retrieved sections/corrections in the latest turn.
   Call Gemini with a JSON `responseSchema`.
4. Apply the coverage gate (no sections ⇒ `not_covered` + escalation; citations limited to
   provided sections) and persist the assistant message with retrieval scores, corrections
   used, model, tokens and latency; the conversation's `last_message_at` and `last_coverage` are
   stamped so the history list and its coverage filter are indexed lookups. Provider failures are persisted as `failed` turns with the
   reason so the UI can retry.

## Evaluations (`eval/`)

Offline, run against the real Gemini API with the key from `.env`; results are written to
`docs/evals/` and discussed in `docs/evaluation-report.md`.

```sh
pnpm exec tsx eval/retrieval-eval.ts --dims 768,1536,3072   # ranking + coverage-gate thresholds + hybrid experiment
pnpm exec tsx eval/corrections-eval.ts                      # few-shot effect of corrections, model-as-judge
```

## Testing strategy

- Unit: config, JWT, chunker, parsers, prompt builder, coverage gate, public-route derivation.
- Integration: Fastify `inject` through the real generated SDK on PGlite (pgvector included),
  with an in-memory queue, a fake embedder and a fake chat model: auth, companies, ingestion
  (queued→ready, supersede, rollback, retry), chat (grounding, instructions, not covered,
  failure + retry, pagination), feedback (validation, few-shot injection, deactivation).
- No test talks to Gemini or needs Docker. `TEST_LOG_LEVEL=info pnpm test` shows api logs.
